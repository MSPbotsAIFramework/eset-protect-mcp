## Requirement understanding

One line: Manage endpoint security and EDR data across US/EU/DE/JPN/CA regions via ESET PROTECT.

The requester wants an Agent-platform connector for ESET PROTECT that lets an agent see and act on
endpoint security data (managed devices, EDR detections, security policies) for a tenant whose ESET
PROTECT / ESET Inspect / ESET Cloud Office Security server is hosted in one of five regions (US, EU,
DE, JPN, CA). The ticket's own link (`conduit.wyre.ai/plugins/eset-protect`) is a third-party
marketplace's generic marketing page, not ESET's documentation (see Current state). No specific tool,
bug, or workflow is named beyond "manage ... data" — the scope below is DEV01's reading of that phrase
against ESET's actual public API surface, recorded as an explicit decision (see "Decisions made by

## Product design

### Goals / Non-goals

**Goals (v1):**
- Let an agent list the endpoints (devices and device groups) ESET PROTECT manages for a tenant.
- Let an agent see EDR detections for that tenant (list + get a single detection) and resolve one by
  its id — the one explicit "manage ... EDR data" write action the ticket's wording supports without
  guessing at a workflow it doesn't name.
- Let an agent see and change which security policy is applied to a device or group (list policies,
  get a policy, list/assign/unassign policy assignments).
- Make all of the above reachable the same way every other MSPbots connector is: one MCP tool call per
  capability, credentials supplied per-request via Header, one host selected by a region Header.

**Non-goals (v1):**
- No device lifecycle writes (move, rename, create, delete, master-device toggling) — the ticket does
  not name a device-management workflow, and SOP §2.7 defaults new tools to read-only absent an
  explicit business need.
- No ESET Inspect EDR rule/exclusion authoring, no incident-comment or indicator management beyond
  reading/resolving a detection.
- No ESET MSP Administrator 2, Hub, Secure Authentication (2FA), or Threat Intelligence APIs — none of
  those map to "endpoint security and EDR data"; MSP Administrator is partner billing/provisioning, Hub
  is role-gated for MSP/distributor staff, Secure Authentication is a 2FA add-on for other apps, Threat
  Intelligence is a separate portal-replacement feed.
- No UI changes. This is a backend-only connector; it surfaces through the Agent platform's existing
  generic connector-connect dialog (`wiki: ProductDocs/_connector-fields.md` § 83, variant 1) once
  registered — that dialog's behavior is unmodified by this ticket.

### Acceptance criteria AC1..AC14

- AC1: Given a `tools/list` call with any valid credential Headers, When the server responds, Then it
  returns exactly the `eset_*` tool set defined in Tech design §4 (11 tools), each description
  ≤ 500 characters with no ESET-internal endpoint names or implementation detail in the text.
- AC2: Given a `POST /mcp` request missing any of `X-Eset-Username`, `X-Eset-Password`,
  `X-Eset-Region`, When the server handles it, Then it returns HTTP 401 listing the missing Header
  name(s) in the body, and no request is made to ESET Connect.
- AC3: Given `GET /health` with no Headers at all, When ESET Connect is unreachable or slow, Then the
  endpoint still returns 200 `{"status":"ok"}` — the health check never calls ESET's API.
- AC4: Given a `tools/call` to `eset_list_devices` with no `limit`, When it succeeds, Then the result
  is capped at the default limit (≤ 50) with `has_more` set if more devices exist; a `limit` above the
  hard cap (200) is clamped to 200, not rejected.
- AC5: Given a `tools/call` to `eset_get_device` with a `deviceUuid` ESET Connect reports as not found,
  When the call completes, Then the tool returns `{"error":{"code":"not_found","retryable":false}}`,
  not an unhandled exception or a 500.
- AC6: Given a `tools/call` to `eset_list_detections` with a status/severity filter that matches
  nothing, When it succeeds, Then it returns an empty array (not a `not_found` error); given no filter,
  Then it applies the same pagination cap and `has_more` behavior as AC4.
- AC7: Given a `tools/call` to `eset_resolve_detection` with a `detectionUuid` already in a resolved
  state, When ESET Connect reports that as a conflict or a no-op success, Then the tool maps it to a
  structured outcome (success echoing the current state, or `invalid_argument`) — never an unhandled
  exception.
- AC8: Given a `tools/call` to `eset_assign_policy`, When the arguments are checked, Then it requires
  one explicit `deviceUuid` or `groupUuid` plus one `policyUuid` — no wildcard, "all devices", or
  group-pattern targets are accepted — and the tool is annotated `destructiveHint=true`.
- AC9: Given a `tools/call` to `eset_unassign_policy` with an `assignmentUuid` that does not exist,
  When ESET Connect returns 404, Then the tool returns
  `{"error":{"code":"not_found","retryable":false}}`, not a 500.
- AC10: Given ESET Connect returns HTTP 429 on an outbound call, When the tool is handling a request,
  Then it retries with backoff honoring `Retry-After` within the single-call 120s budget (SOP §5), and
  if still failing returns `{"error":{"code":"rate_limited","retryable":true}}`.
- AC11: Given two concurrent `tools/call` requests carrying two different tenants' credential Headers,
  When both are in flight on the same running container, Then neither response, nor the JWT used to
  make it, nor the selected regional host leaks into the other request — the only state shared across
  requests is the credential-fingerprinted, expiring JWT cache described in Tech design §7.
- AC12: Given the same credential+region Headers are reused within 55 minutes, When a second tool call
  arrives, Then the service reuses the cached JWT (no second password-grant call to ESET); given 55
  minutes have elapsed, Then it re-authenticates. The cached JWT is never written to a log line or
  returned to the MCP caller.
- AC13: Given a fresh clone of the repo, When reading `README.md`, Then it documents all three required
  Headers (name, required, meaning, where to obtain/configure them) in the §3.1 table format and
  includes the MSPbots Connector section verbatim per SOP §0.5.
- AC14: Given the full tool list, When compared against the Non-goals above, Then no tool exposes device
  lifecycle writes, EDR rule/exclusion authoring, MSP Administrator, Hub, Secure Authentication, or
  Threat Intelligence operations.

## Tech design

### Conclusion

Build a new Python 3.12 + uv + FastMCP service in the existing empty `MSPbotsAIFramework/eset-protect-mcp`
scaffold, following the SOP §9 recommended layout. One HTTP client wraps ESET Connect's REST gateway
(single OAuth2-password-grant auth shared across its device/policy/detection sub-APIs); three Header
credentials (`X-Eset-Username`, `X-Eset-Password`, `X-Eset-Region`) select the tenant and region per
request; 11 tools cover devices, detections, and policies read/write as scoped in Product design. This
is the only reasonable approach — there is no existing code in the repo to extend, and no other MSPbots
repo implements this vendor.

### Where the current implementation lives

Nothing exists yet. `README.md` @ be47d42 is the entire repo (Current state). There is no
`src/`, `tests/`, `pyproject.toml`, or `Dockerfile` to extend — this is SOP "Main line A" (new service,
first version), not "Main line B" (modify an existing one).

### Data & API contract

**Credential Headers** (declared in README per SOP §3.1; read in `auth.py`/`api_client.py`, never
logged, never falls back to an environment variable):

| Header | Required | Meaning | Where to obtain |
|---|---|---|---|
| `X-Eset-Username` | Yes | ESET Connect API User username | ESET PROTECT/Inspect console → create an API User account (`help.eset.com/eset_connect/en-US/create_api_user_account.html`) |
| `X-Eset-Password` | Yes | ESET Connect API User password | Same API User account |
| `X-Eset-Region` | Yes | One of `eu`, `de`, `us`, `ca`, `jpn` — must match the region hosting the tenant's ESET PROTECT/Inspect/Cloud Office Security server | Known by the tenant admin; ESET does not expose a region-discovery endpoint in its public docs |

**Auth flow** (internal, not a tool): `api_client.py` exchanges Username+Password for a JWT via the
region's OAuth2 password-grant endpoint on first use per credential+region pair, caches it in-process
keyed by `sha256(username + ":" + region)` with the vendor's own expiry minus a 5-minute safety margin
(§7), and attaches it as `Authorization: Bearer <jwt>` on every subsequent ESET Connect call for that
cache entry.

**Tools** (11, all prefixed `eset_`, SOP §2.8 naming; all return a JSON string per SOP §4.1):

| Tool | Method + path (ESET Connect) | Args | Annotations |
|---|---|---|---|
| `eset_list_device_groups` | `GET /v1/device_groups` | `limit` (≤50 default, ≤200 hard cap) | `readOnlyHint` |
| `eset_list_devices` | `GET /v1/devices` | `groupUuid?`, `limit` | `readOnlyHint` |
| `eset_get_device` | `GET /v1/devices/{deviceUuid}` | `deviceUuid` | `readOnlyHint` |
| `eset_list_detections` | `GET /v2/detections` (path confirmed in dev, see Open questions) | `status?`, `severity?`, `deviceUuid?`, `limit` | `readOnlyHint` |
| `eset_get_detection` | `GET /v2/detections/{detectionUuid}` | `detectionUuid` | `readOnlyHint` |
| `eset_resolve_detection` | `POST /v2/detections/{detectionUuid}:resolve` | `detectionUuid`, `note?` | `destructiveHint` |
| `eset_list_policies` | `GET /v2/policies` | `limit` | `readOnlyHint` |
| `eset_get_policy` | `GET /v2/policies/{policyUuid}` | `policyUuid` | `readOnlyHint` |
| `eset_list_policy_assignments` | `GET /v2/policy-assignments` | `deviceUuid?`, `groupUuid?`, `limit` | `readOnlyHint` |
| `eset_assign_policy` | `POST /v2/policy-assignments` | `policyUuid`, one of `deviceUuid`/`groupUuid` (required, exclusive) | `destructiveHint` |
| `eset_unassign_policy` | `DELETE /v2/policy-assignments/{assignmentUuid}` | `assignmentUuid` | `destructiveHint` |

**Response shape**: each `list` tool returns `{"items": [...], "has_more": bool}`; `get` tools return the
single resource object trimmed to agent-relevant fields (drop ESET-internal/audit-only fields); errors
always use the SOP §4.2 envelope `{"error":{"code","message","retryable"}}`.

**Backward compatibility**: not applicable — this is the first version of a brand-new tool set, nothing
is registered on the gateway yet (confirmed by the "new vendor" registration path in Tech design §8).

### Key flow / sequence

```
Agent -> Gateway -> POST /mcp (X-Eset-Username, X-Eset-Password, X-Eset-Region, tools/call eset_list_detections)
  -> eset-protect-mcp middleware: read 3 Headers into ContextVar, 401 if any missing
  -> tools/detections.py: build filters from args
  -> auth.py: cache hit? use cached JWT : POST {region-host}/.../token (password grant) -> cache JWT (fingerprint = sha256(user+region), ttl = 55m)
  -> api_client.py: GET {region-host}/v2/detections?... with Authorization: Bearer <jwt>
     -> 200: trim fields, apply limit/has_more -> return JSON string
     -> 401/403: return {"error":{"code":"unauthorized","retryable":false}}
     -> 404: return {"error":{"code":"not_found","retryable":false}}   (only for single-resource get, not list)
     -> 429: retry with backoff honoring Retry-After, else {"error":{"code":"rate_limited","retryable":true}}
     -> 5xx/timeout: retry (bounded), else {"error":{"code":"upstream_error","retryable":true}}
  -> ContextVar reset in `finally`
```

### Non-functional

- **Idempotency & concurrency**: credential isolation via `ContextVar` set/reset per request (SOP §3.3);
  no module-level or global credential/token state except the fingerprinted, expiring JWT cache (§7),
  which is explicitly the one exception SOP §3.4 allows. `eset_unassign_policy` and
  `eset_get_*`/`eset_list_*` are naturally idempotent; `eset_resolve_detection` and
  `eset_assign_policy` are not annotated `idempotentHint` since ESET's documented behavior for
  re-resolving/re-assigning is not confirmed (AC7) — the error mapping must not crash either way.
- **Performance**: `list` tools default `limit=50`, hard cap `200`; responses trimmed to agent-relevant
  fields and truncated at 20,000 characters with `has_more` if still over (SOP §2.5). A single tool
  call's total latency budget (including the JWT exchange on a cache miss, plus retries) stays under
  120s (SOP §5).
- **Security**: credentials never leave the request Header → `ContextVar` → outbound `Authorization`
  path; never logged (SOP §6, §11); the cached JWT is in-process memory only, never persisted to disk,
  never returned to the MCP caller, keyed by a hash (not the raw credential) so a log of cache keys
  alone cannot recover a password.
- **Multi-tenant isolation**: every outbound call is scoped to the requesting tenant's own
  Username+Region via the per-request `ContextVar`; the JWT cache key includes both username and
  region so two tenants, or the same tenant's two regions, never share a cache entry.
- **Observability**: structured logs include tool name, a non-sensitive arg summary (e.g. `limit`,
  `status` filter — never the Username/Password Headers), the ESET Connect path and status code,
  latency, and the mapped error `code`; never the JWT or raw credentials (SOP §6).

### Decisions made by DEV01

- Chose **ESET Connect** as the single integration surface (not the On-Prem REST/Server APIs, not
  Inspect On-Prem, not MSP Administrator/Hub/Secure Authentication/Threat Intelligence) — it is the one
  ESET public API documented as a multi-tenant SaaS gateway covering devices, detections, and policies
  in one OAuth model, which fits the Header-credential, no-persisted-per-tenant-config MCP contract;
  the On-Prem APIs assume direct network reachability to a self-hosted server per tenant, which this
  connector shape cannot express. Alternative considered: On-Prem REST API — rejected, see Option
  analysis.
- Targeted the **v2** detection/incident generation, not v1 (older) or v3 (incident-centric, a
  different resource shape) — v2 is what the ticket's own prior research already named, and its
  per-detection resource model lines up with "devices, detections, policies" as three parallel
  resource families the way v1/v3 do not as cleanly. Alternative: v3 — rejected for this version as a
  larger, differently-shaped surface; could be a follow-up once an incident-centric workflow is named.
- Scoped v1 to **read + one resolve action for detections, read + assign/unassign for policies, read
  only for devices** — the ticket says "manage ... data" without naming a specific write workflow;
  SOP §2.7 defaults new write tools to "no, unless a business need is named", and resolving a detection
  / (re)assigning a policy are the two actions an EDR-triage agent flow most plausibly needs. Device
  lifecycle writes (move/rename/create/delete) were left out as a follow-up since nothing in the ticket
  names a device-provisioning use case. Alternative: expose the full device/policy/detection write
  surface ESET documents — rejected as scope creep beyond what "manage ... data" supports.
- Selected **`X-Eset-Region` as a required Header enum**, not an auto-detected region — ESET's own docs
  tell the *human* API-user owner to pick the host matching where their server is hosted; there is no
  documented "which region is my tenant in" discovery call, so the Header is the only option consistent
  with "credentials only from Header" / no persisted per-tenant config. Alternative: a single global
  host with
  server-side fallback across all five regions — rejected, it would silently multiply outbound calls
  5x per request and leak timing information between regions.
- Added an **in-process, credential-fingerprinted, expiring JWT cache** (keyed by
  `sha256(username+region)`, TTL = vendor's 60-minute lifetime minus 5 minutes) rather than
  re-authenticating on every tool call — SOP §3.4 explicitly allows this one exception to "no
  cross-request caching" when the cache key is bound to the credential and expires; re-authenticating
  via password grant on every call would be wasteful and more likely to trip ESET's own rate limiting.
  Alternative: no caching (re-auth every call) — rejected as needless load and latency; alternative:
  cache without a credential-bound key — rejected, that is exactly the cross-tenant leak §3.4 forbids.

## Implementation note: Swagger lookup resolved three Open questions (dev leg)

The design's Open questions flagged the exact detection paths, the region host pattern, and the
pagination story as unconfirmed, to be resolved "in dev" against ESET's live Swagger. That lookup
happened during implementation (2026-11-02) and corrected three assumptions; **tool names,
parameters, and external contract are unchanged** (as the Open question anticipated), only
`api_client.py`'s URL templates, request/response unwrapping, and the pagination mechanism changed:

1. **ESET Connect is not one gateway host per region.** The help-center prose implied a single
   `{region}.esetconnect.eset.systems` host; the live Swagger `servers` entries for each API family
   show four separate per-region hosts instead, confirmed by fetching the real specs linked from
   `https://eu.esetconnect.eset.systems/swagger/swagger-initializer.js`:
   - Auth (OAuth2 token): `{region}.business-account.iam.eset.systems`, `POST /oauth/token` — not
     `/v1/oauth-provider/token` on the gateway host, which 301-redirects to `/swagger` (confirmed
     live: `curl -X POST https://eu.esetconnect.eset.systems/v1/oauth-provider/token` → `301` →
     `location: https://eu.esetconnect.eset.systems/swagger`).
   - Device management: `{region}.device-management.eset.systems` (`/v1/devices`,
     `/v1/device_groups`, `/v1/device_groups/{groupUuid}/devices` — paths otherwise as designed).
   - Incident management: `{region}.incident-management.eset.systems` (`/v2/detections` as designed).
   - Policy management: `{region}.policy-management.eset.systems` (`/v2/policies`,
     `/v2/policy-assignments` as designed).
   A single JWT from the auth host is a bearer token accepted by all three resource hosts — confirmed
   live: an invalid bearer against `device-management`/`policy-management`/`incident-management`
   uniformly returns `401 Token has expired or is invalid`, not a host-specific auth error — so the
   JWT cache stays keyed by username+region only (`auth.py`), independent of which resource domain a
   call targets. Region slugs `eu/de/us/ca/jpn` all resolve on every host family (checked live with
   `curl` against all five region subdomains on `device-management.eset.systems`), confirming the
   Open question's assumed slug set.
2. **Pagination is server-side**, not undocumented as the help page implied: every list endpoint
   used here (`/v1/device_groups`, `/v1/devices`, `/v1/device_groups/{groupUuid}/devices`,
   `/v2/detections`, `/v2/policies`, `/v2/policy-assignments`) accepts `pageSize`/`pageToken` and
   returns `nextPageToken`. The service now sends `pageSize=<clamped limit>` and treats a non-empty
   `nextPageToken` as `has_more`, instead of fetching everything and slicing client-side
   (`pagination.py: build_page`/`has_more_page`). `/v2/detections` does **not** support
   `status`/`severity`/`deviceUuid` filter params though — those remain client-side filters applied
   to the fetched page (`tools/detections.py: _matches_filters`, against the Detection object's own
   `resolved`/`severityLevel`/`device.uuid` fields), which can miss matches on a later page; ESET's
   v2 detections API has no search endpoint for this ticket's scope. Noted as a known limitation,
   not a defect — an incident-centric v3 search (`/v3/incidents`) exists but is out of scope (Product
   design Non-goals).
3. **Response envelopes wrap single resources and some write bodies**, confirmed from each domain's
   schema definitions: `GET /v1/devices/{uuid}` → `{"device": {...}}`; `GET /v2/detections/{uuid}` →
   `{"detection": {...}}`; `GET /v2/policies/{uuid}` → `{"policy": {...}}`;
   `POST /v2/policy-assignments` body and response wrap `{"assignment": {"policyUuid", "target":
   {"deviceUuid"|"deviceGroupUuid"}}}` — the target field names are `deviceUuid`/`deviceGroupUuid`,
   not the `deviceUuid`/`groupUuid` first assumed; the external tool parameter name `group_uuid` is
   unchanged, only the wire-level field name sent to ESET differs (`tools/policies.py`).
   `/v2/policy-assignments` list filters by `target.deviceUuid`/`target.deviceGroupUuid` (dotted
   query param names), not bare `deviceUuid`/`groupUuid`.

None of this changes the Product design's Goals/Non-goals/ACs or the Tech design's tool list,
parameters, or error contract — it only corrects the URL templates and wire-level field names behind
them, exactly the scope the Open question called out as safe to fix without redesign.
